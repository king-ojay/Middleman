# Middleman runbook

How to run the tests, the Part A experiment and a pilot session, and what the
system does not do yet. Commands run from the repo root unless they start with
`cd`. Node 24 (`.nvmrc`), MongoDB as a one-node replica set (see README, "Run
it locally").

> **`npm run seed` wipes whatever `MONGO_URI` points at**, and `server/.env`
> may point at Atlas (the live database). Always pass a local `MONGO_URI` on
> the command line for seeds, tests and scripts, as below.

## 1. Run the tests

```bash
cd server
npm test                                    # unit tests only; API tests are skipped
TEST_MONGO_URI='mongodb://localhost:27017/middleman_test?directConnection=true' npm test   # everything
```

- The API tests need a replica set (rating writes and escrow moves are
  transactions), hence `?directConnection=true`. The database name must
  contain "test"; the API test files drop and refill it (the escrow and
  security files use their own suffixed copies).
- Expected at release: 112 tests, 112 pass, 0 skipped.
- Escrow runs on the fake payment provider in tests; `test/momoSandbox.test.js`
  checks the MoMo request shapes against a stubbed `fetch` (no network).

Ranking regression (positive-only rankings must not change, 300 rankings):

```bash
cd server
MONGO_URI='mongodb://localhost:27017/middleman_regression?directConnection=true' node seed.js
MONGO_URI='mongodb://localhost:27017/middleman_regression?directConnection=true' node scripts/rankingRegression.js
```

## 2. Run the experiment (Part A)

The datasets are not in the repo (`data/raw/` is gitignored, never commit it).

```bash
mkdir -p data/raw
curl -L -o data/raw/soc-sign-bitcoinotc.csv.gz https://snap.stanford.edu/data/soc-sign-bitcoinotc.csv.gz
curl -L -o data/raw/soc-sign-bitcoinalpha.csv.gz https://snap.stanford.edu/data/soc-sign-bitcoinalpha.csv.gz   # optional

cd server
node scripts/experiments/run.js --dataset bitcoinotc --sample 2000            # quick check, ~20 s
node scripts/experiments/run.js --dataset bitcoinotc                          # all 35,592 edges, ~4.5 min
node scripts/experiments/run.js --dataset bitcoinotc --tune-split --seed 2    # held-out tuning (as reported)
node scripts/experiments/run.js --dataset bitcoinalpha                        # replication
```

- Check the logged MD5 (OTC `eeaf5cd1d29ab435505baeeb6816317b`) and line count
  (35,592) before trusting a run.
- Each run writes `results/<dataset>_<timestamp>.json` and `.csv` (aggregate
  metrics only). Commit only the runs you report. The JSON records the git
  commit and a hash of the experiment code, and flags a dirty `server/` tree.
- Compare against Kumar et al. (2016) Table IV only (unsupervised
  leave-one-out). Reported OTC numbers are in CLAUDE.md / the README.

## 3. Start a pilot session

### Before the first session (once)

The full flow (OTP signup → job → offers → escrow → confirm/release → ratings
both ways → ranking change, plus the dispute path) passed in a browser against
a local production build at v1.0.0-pilot. The live API still runs `main`
(before escrow), so **the deployed run happens after redesign-v2 is merged into
main**: repeat that flow on the live URLs once the merge has deployed.

1. **Deploy** API (Render) and app (Vercel) from main after the merge; check
   `https://middleman-api-74zb.onrender.com/api/health` returns
   `{"status":"ok"}`.
2. **Database**: the pilot uses its own Atlas database, not the seeded demo
   data. Point Render's `MONGO_URI` at an empty database (e.g.
   `…/middleman_pilot?…`). Do not run `npm run seed` against it.
3. **SMS**: signup needs an OTP. With `OTP_PROVIDER=console` the production API
   never shows the code, so set `OTP_PROVIDER=africastalking` with
   `AT_USERNAME`, `AT_API_KEY` (and `AT_SENDER_ID` if approved) in Render.
4. **Payments**: escrow stays sandbox. `PAYMENT_PROVIDER=fake` works with no
   keys. For the MTN sandbox, run `server/scripts/momoSandboxSetup.js`, then
   `momoSandboxCheck.js`, set the six `MOMO_*` keys and `MOMO_CALLBACK_URL` in
   Render, then `PAYMENT_PROVIDER=momo-sandbox`. Never a production MoMo host:
   the provider refuses anything but `sandbox.momodeveloper.mtn.com`.
5. **Admin secret**: copy `ADMIN_SECRET` from Render (generated by
   `render.yaml`) into your password manager; it settles disputes.
6. **Check security on the live URLs** (all passed at release):
   ```bash
   API=https://middleman-api-74zb.onrender.com
   curl -sI http://middleman-api-74zb.onrender.com/api/health | head -1    # 301 to https
   curl -sI $API/api/health | grep -i strict-transport                       # HSTS
   curl -s -H 'Origin: https://evil.example' $API/api/health                 # 403 Origin not allowed
   ```

### Each session

1. **Wake the API** 2 minutes before: open the health URL (free Render
   instances sleep after 15 minutes idle; the first request takes ~50 s).
2. **Consent first**, then give the participant their participant ID (P-001,
   P-002, … from your paper consent list; see the limitations below).
3. The participant opens https://middleman-client.vercel.app on their own
   phone, registers (role, trades, name, phone, area, SMS code, PIN, optional
   "Who invited you?"). Point out the yellow "Sandbox – no real money" banner.
4. Tasks (record time and success on paper against the participant ID):
   - Client: find a worker in Discover; post a job; choose an offer; pay into
     escrow; confirm the job is done and rate the worker.
   - Worker: find the job in Open jobs; accept or counter; start; mark complete;
     rate the client after payment.
5. **Disputes** ("Report a problem", open to either side once the money is
   held) lock the money. Settle them with the admin routes:
   ```bash
   H="X-Admin-Secret: $ADMIN_SECRET"
   curl -s -H "$H" $API/api/admin/disputes                       # disputed jobs (ids, no names or phones)
   curl -s -H "$H" $API/api/admin/jobs/<jobId>/ledger            # every escrow record
   curl -s -X POST -H "$H" $API/api/admin/jobs/<jobId>/release   # pay the worker
   curl -s -X POST -H "$H" $API/api/admin/jobs/<jobId>/refund    # repay the client
   ```
   A payment that stays "pending" settles when MoMo calls back or when the job
   page polls (every 5 s while it is open).
6. SUS and the personalised-vs-flat ranking-preference questions on the paper
   or Google Form, keyed by participant ID only.

### After the pilot

Delete all pilot accounts, ratings and logs (ethics commitment). The deletion
script is not built yet (see below), so this must be built before the pilot.

## 4. Known limitations

**Not built, needed for the pilot (ethics form):**
- Participant IDs (P-001…) are not stored on accounts, and there are no task or
  event logs in the app. Times and outcomes are recorded outside it for now.
- No script to delete all pilot accounts, ratings and event logs.
- SUS and ranking-preference answers are not collected in the app, and there is
  no flat-ranking view to compare against.

**Deployment:**
- Live signup needs a real SMS provider. Africa's Talking LIVE is chosen but
  not switched on, so OTP signup and PIN reset do not work on the live URL yet.
- Render free tier: sleeps when idle (~50 s cold start), one instance. Rate
  limits and lockouts are in memory, so a restart clears them.
- The app's CSP (`client/vercel.json`) allows only
  `https://middleman-api-74zb.onrender.com`. A preview or second API host must
  be added to `connect-src`, and the Vercel URL to the API's `CORS_ORIGINS`.
- Not installable as a PWA yet: no web manifest, service worker or favicon.

**Escrow:**
- Sandbox only, no real money. Never tested against the real MTN sandbox (no
  keys at release); the fake provider and stubbed request shapes are tested.
- Every MoMo payer and payee is the sandbox test number
  (`MOMO_SANDBOX_MSISDN`), never a participant's phone; amounts go as EUR, the
  sandbox currency.
- One payment covers the full agreed price; the materials deposit is shown but
  not paid separately. No 72-hour auto-release. Disputes are settled by the
  researcher through the admin API (no admin screen or role).
- With the fake provider, a payment that is pending when the API restarts can
  stay pending (the fake keeps its records in memory). It settles in the same
  request, so this needs a crash mid-request.

**Ratings and trust:**
- Ratings need the job confirmed and the escrow released, in both directions;
  disputed or resolved jobs get no ratings.
- App defaults are λ 0.5, depth 3. Held-out tuning on Bitcoin OTC chose λ 1.5,
  depth 2; switching is the researcher's decision.
- The public datasets test only the core (paths, decay, strongest path,
  negative evidence). Referral boost, area fallback, verification floor and
  escrow are evaluated in the pilot.
